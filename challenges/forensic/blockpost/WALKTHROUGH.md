# Blockpost — авторский разбор

В `blockpost.zip` два файла:

- `challenge.pcap` — трафик клиента `10.0.0.50` с сервером `10.0.0.10:25565`, 1633 кадра,
  3 октября 2026, 19:47 UTC;
- `latest.log` — лог Minecraft-клиента Kolya (Fabric + мод `netdebug`).

Флаг выложен шерстью на стене у спавна. Чтобы его увидеть, нужно восстановить, какие блоки
сервер разослал клиенту, а для этого — расшифровать соединение.

## Шаг 0. Что за трафик

В pcap два TCP-соединения к порту `25565`, стандартному порту Minecraft Java Edition. Wireshark
этот протокол не разбирает.

**Первое соединение (`:51034`, 10 кадров)** — status ping: так клиент опрашивает сервер для
списка серверов. Оно не шифруется, и в ответе сервера виден JSON:

```json
{"version":{"name":"26.3","protocol":777},"players":{"max":20,"online":2,
 "sample":[{"name":"Vasya_Builder",…},{"name":"petya2011",…}]},…}
```

Версия 26.3, протокол 777: все ID пакетов берём из таблицы для этой версии
(minecraft.wiki → Java Edition protocol → Packets).

**Второе соединение (`:51036`, ~1600 кадров, 46 с)** — сама игра. Первый клиентский сегмент:

```
10 00 89 06 09 31 30 2e 30 2e 30 2e 31 30 63 dd 02 | 17 00 05 4b 6f 6c 79 61 bb 54 aa c4 …
│  │  └───┘ │  └──────── "10.0.0.10" ──────┘ └───┘ │   │  │  │  └ "Kolya" └ UUID (16 байт)
│  │  777   └ длина строки адреса = 9         25565 intent = 2 (login)
│  └ ID 0x00 (handshake / intention)          │  └ ID 0x00 Login Start
└ длина кадра = 16                            └ длина = 23
```

`89 06` — VarInt: `0x09 | (0x06 << 7) = 777`.

## Шаг 1. Reassembly

Каждое направление собираем отдельно по номерам последовательности. В Wireshark для этого
есть *Follow → TCP Stream*: сначала выбрать сторону, затем *Show as Raw* и *Save as*.

Важно: для расшифровки нужен **точный** байтовый поток. CFB8 — потоковый режим, где каждый
байт шифртекста влияет на следующие 16, поэтому один лишний или потерянный байт портит всё
дальше. В варианте `--lossy` наивная склейка payload'ов в порядке файла ломается из-за
ретрансмиссий и out-of-order.

## Шаг 2. Открытая часть логина

До обмена ключами пакеты идут без шифрования и без компрессии, формат
`VarInt Length | VarInt ID | Data`.

Сервер → клиент, первый кадр — **Encryption Request** (login, `0x01`):

```
ac 01               Length = 172
01                  ID 0x01 Encryption Request
00                  Server ID = "" (у vanilla всегда пусто)
a2 01 30 81 9f …    Public Key: 162 байта DER SubjectPublicKeyInfo (RSA-1024)
04 e1 81 1b 4c      Verify Token: 4 байта = e1811b4c
01                  Should authenticate = true (online mode)
```

Клиент → сервер, после handshake — **Encryption Response** (login, `0x01`):

```
85 02  01  80 01 <128 байт>  80 01 <128 байт>
│      │   └ shared secret, RSA/PKCS#1 v1.5   └ verify token, тоже под RSA
│      └ ID 0x01
└ Length = 261
```

Это ровно то, что описано в статье Protocol Encryption на wiki: 16-байтный shared secret,
зашифрованный открытым ключом сервера. Приватного ключа у нас нет, а RSA-1024 честный.
Значит, секрет нужно найти в другом месте.

## Шаг 3. Ключ из `latest.log`

Мод `netdebug` пишет в DEBUG каждую login-сессию:

```
[22:47:13] [Render thread/INFO]: Connecting to 10.0.0.10, 25565
[22:47:13] [Netty Client IO #5/DEBUG] (netdebug) << hello server_id="" public_key=RSA-1024 fp=sha1:8cd13d42… verify_token=e1811b4c should_authenticate=true
[22:47:13] [Netty Client IO #5/DEBUG] (netdebug) session join: server_hash=…
[22:47:13] [Netty Client IO #5/DEBUG] (netdebug) cipher enabled: AES/CFB8/NoPadding secret=5e19fde90cf9b4838622421e57a12862
```

В логе **четыре** сессии с шифрованием:

| Время (МСК) | Сервер | Отпечаток ключа | Чем закончилась |
|---|---|---|---|
| 22:31 | 203.0.113.37 (CraftLand) | `60bedba7…` | вышел сам |
| 22:43 | 10.0.0.10 | `8cd13d42…` | `Timed out` через 42 с |
| **22:47** | **10.0.0.10** | **`8cd13d42…`** | **вышел сам — это наш pcap** |
| 23:02 | 10.0.0.10 | `0a5e4f0d…` (сервер перезапущен после отката) | `You are banned…` |

Сессии 2 и 3 идут к одному серверу с одним и тем же RSA-ключом: vanilla генерирует пару
ключей при старте и держит её до перезапуска. По отпечатку их не различить. Различает
**verify token** — он случайный для каждого подключения и виден в pcap открытым текстом
(`e1811b4c`).

Время тоже сходится: лог в МСК (UTC+3), pcap в UTC. `22:47:13` ↔ `19:47:13Z`.

Для проверки можно посчитать server hash: `sha1("" + secret + DER)` в «минекрафтовском» виде
(знаковое число в hex). Он должен совпасть со строкой `session join: server_hash=…` той же сессии.

## Шаг 4. Расшифровка

Из статьи Protocol Encryption:

- шифр **AES-128/CFB8** (сегмент 8 бит), **key = IV = shared secret**;
- на каждое направление свой экземпляр шифра, и он **не перезапускается** между пакетами:
  это один непрерывный поток;
- шифруется всё, включая поле длины;
- клиент шифрует всё **после** своего Encryption Response, сервер — всё после Encryption
  Request. Первый зашифрованный пакет сервера — Set Compression.

```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms
from cryptography.hazmat.decrepit.ciphers.modes import CFB8   # или Crypto.Cipher.AES MODE_CFB, segment_size=8
dec = Cipher(algorithms.AES(secret), CFB8(secret)).decryptor()
plain = dec.update(s2c[174:])        # 174 = конец Encryption Request в потоке сервера
```

```
шифртекст: b4 75 fe 57 26 56 63 27 31 97 56 d3 d4 13 2f 75 …
открытый:  03 03 80 02 | fe 06 c6 08 78 9c 45 8f …
           │  │  └───┘   │     │     └ zlib
           │  │  256     │     └ Data Length = 1094 (несжатый размер)
           │  └ ID 0x03  └ Packet Length = 894
           └ Length = 3  → Set Compression, порог 256
```

Если секрет неверный, первый кадр — мусор. Из четырёх секретов лога подходит ровно один.

## Шаг 5. Компрессия и фазы

После Set Compression каждый кадр (в обе стороны) выглядит так:

```
VarInt Packet Length   — длина (Data Length + остальное)
VarInt Data Length     — длина несжатых (ID + Data); 0 = кадр не сжат
payload                — zlib(ID + Data) или ID + Data как есть
```

Пакеты короче 256 байт идут с `Data Length = 0`, длинные (Login Success, реестры, теги, чанки)
сжаты. Один и тот же ID в разных фазах значит разное, поэтому нужен конечный автомат:

| Фаза | Что приходит | Переход |
|---|---|---|
| login | Set Compression `0x03`, Login Success `0x02` | `0x02` → configuration |
| configuration | brand `0x01`, Feature Flags `0x0D`, Known Packs `0x0F`, 11× Registry Data `0x07`, Update Tags `0x0E` | Finish Configuration `0x03` → play |
| play | Login `0x32`, Player Position `0x49`, 98× Chunk Data `0x2E`, chunk batches `0x0C`/`0x0B`, Set Center Chunk `0x60`, **363× Block Update `0x08`**, 151× Acknowledge Block Change `0x04`, Keep Alive `0x2D`, System Chat `0x7C` … | — |

Заметьте ловушку: `0x03` в login — это Set Compression, а в configuration — Finish Configuration.

## Шаг 6. block_update и Position

`block_update` (play, clientbound, `0x08`): `Position` (8 байт) + `VarInt` block-state. Первый
такой пакет в потоке:

```
0c                          Packet Length = 12
00                          Data Length = 0 (не сжат)
08                          ID 0x08 → block_update
00 00 1e 00 00 04 80 49     Position, v = 0x00001e0000048049
b3 10                       block-state VarInt = 0x33 | (0x10 << 7) = 2099
```

`Position`: `x` (26 бит) | `z` (26 бит) | `y` (12 бит), потом знаковое расширение:

```
x = v >> 38               = 120
z = (v >> 12) & 0x3FFFFFF = 72
y =  v & 0xFFF            = 73
```

Это блок 2099 (лаймовая шерсть) в `(120, 73, 72)` — кусок **ложной** надписи, см. ниже.

## Шаг 8. Шрифт 5×5

Символы идут с шагом 6: 5 столбцов глифа и 1 пустой. Режем на ячейки и читаем глазами или по
шрифту. У последнего `}` правый столбец пустой, поэтому число ячеек округляем вверх.

`INNOCTF{...}` → флаг (тем, что задали в `CTF_FLAG` при запуске).

## Второй путь: что делал сам клиент

Тот же секрет расшифровывает и поток клиента (с байта 304, после Encryption Response).
Компрессия там тоже с порогом 256: клиент включает её, получив Set Compression, и Login
Acknowledged уже идёт в новом формате.

Фазы клиента переключаются на Login Acknowledged (`0x03`) и Acknowledge Finish Configuration
(`0x03`). В play клиент шлёт:

- 788× Client Tick End `0x0D`;
- 634× Set Player Position `0x1E` — игрок идёт вдоль стены от `x ≈ 115` до `x ≈ 240`;
- **238× Use Item On `0x42`**.

Use Item On: `Hand, Position (цель), Face (VarInt), Cursor XYZ, Inside, World Border Hit,
Sequence`. Все клики — по каменной подложке `z = 63`, грань `3` (+Z). Новый блок встаёт в
`цель + (0, 0, 1)`, то есть ровно в 238 точек надписи на `z = 64`, уже без чужих блоков и шума.
Сервер подтверждает каждую установку `block_update` и `Acknowledge Block Change` с тем же
sequence.

## Ложные следы и как их отсечь

| След | Где | Как отсечь |
|---|---|---|
| Лишние сессии в логе | 4 секрета, у двух сессий к 10.0.0.10 один ключ сервера | verify token из pcap (или время с поправкой МСК/UTC, или пробная расшифровка) |
| Status ping | отдельное открытое соединение | не login (intent = 1); полезен только версией протокола |
| Ложная надпись `NOPE` | `block_update` state 2099 на `z = 72`, 53 блока, ставится постепенно | самая населённая плоскость — `z = 64`; при проекции всего подряд на `(x, y)` `NOPE` ляжет поверх `INNOCTF{` |
| Копание/стройка вокруг | 72 `block_update` (воздух, земля, доски, булыжник) в радиусе 40 блоков | на стену почти не попадают; отсекаются фильтром по доминирующему state |
| Чанки | 98× Chunk Data, в том числе с каменной стеной-подложкой на `z = 63` | это не изменения мира; подложка — это `STONE_BRICKS` внутри секций, а не `block_update` |
| Шум клиента | тики, перемещения, keep-alive | пропускаются по ID |

## Лестница подсказок

1. **Определи протокол.** Какой порт? Что лежит открытым текстом в первом коротком соединении?
2. **Почему дальше мусор?** Прочитай про шифрование протокола: что такое Encryption Request и
   Response, где тут ключ и с какого байта начинается шифртекст.
3. **Ключа в pcap нет.** Что прислал Kolya «в своё оправдание»? Какая из его сессий записана в
   pcap — сравни то, что видно открытым текстом.
4. **После расшифровки.** Сначала Set Compression, дальше кадры в сжатом формате. Следи за фазами
   login → configuration → play. Самый частый пакет сервера в play — `0x08`, `block_update`.
5. **Посмотри на стену.** Выбери плоскость, где блоков больше всего, нарисуй её и раздели на
   клетки 5×5 с пустым столбцом между ними.

## Усложнённые варианты

Генерируются флагами `--axis z` и `--lossy`, которые можно комбинировать. Оба солвера решают
все комбинации, это проверяют тесты.

### `--axis z`

Стена стоит в плоскости `x = 120` (подложка `x = 119`, клики по грани `5`, +X), а текст идёт
вдоль **−z**, как его видит игрок, стоящий с востока и смотрящий на запад. Если искать
плоскость только среди `z = const`, стену не найти. Если взять `z` по возрастанию, надпись
выйдет зеркальной. Солвер перебирает обе плоскости, обе ориентации и сдвиг сетки 0–5.

### `--lossy`

В поток сервера добавлены 6 ретрансмиссий (повтор через RTO 0,2–0,3 с) и 6 перестановок
соседних сегментов. Wireshark помечает их `[TCP Retransmission]`, `[TCP Out-Of-Order]` и `[TCP Previous
segment not captured]` и в Follow TCP Stream собирает правильно. Склейка payload'ов «по порядку в файле» вставляет лишние
байты в шифропоток CFB8, и после первого же повтора расшифровка превращается в мусор.
