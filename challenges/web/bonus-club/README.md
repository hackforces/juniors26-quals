# Клуб Бонус / The Bonus Club (web/medium)

## Условие (для игроков)

**RU:** «Bonus Club» — сервис лояльности магазина: регистрация, welcome-бонус,
клубный магазин призов, VIP-статус с клубной поддержкой, профиль с
аватаркой и описанием. Внутренней рассылкой известно, что у сотрудников
клуба есть служебная награда, но в магазине её не продают. Добудьте её.

**EN:** "Bonus Club" is the store's loyalty service: sign-up, a welcome bonus, a club
prize shop, VIP status with club support, and a profile with an avatar and a bio.
The internal mailing list says club employees have a service award that the shop
never sells. Go and take it.

## Запуск

```bash
CTF_FLAG='InnoCTF{...}' docker compose up -d --build
open http://127.0.0.1:13405/
```

Смена флага — только перезапуск (сидер обновит награду в служебном заказе):

```bash
CTF_FLAG='InnoCTF{...}' docker compose up -d --force-recreate
```

База живёт в контейнере (`/app/data/club.db`): `docker compose restart`
сохраняет её, `--force-recreate` сбрасывает (для CTF это нормально: аккаунты
создаются на лету). `SESSION_SECRET` — из env или случайный на старт.

## Проверка решения

```bash
python3 solve.py http://127.0.0.1:13405   # нужен requests
```

## Описание

Сервис лояльности на Express + SQLite. Магазин с покупкой товаров количеством
1–10 (баланс списывается атомарно), welcome-бонус, VIP-раздел с «письмами в
поддержку» (пишутся в БД, доступны только владельцу), отдельная страница
профиля с загрузкой аватарки и описанием. Три независимые уязвимости образуют
обязательный киллчейн:

1. **Race condition** на `POST /api/bonus`. Проверка «бонус уже получен?»
   (SELECT), скоринг антифродом (await, окно ~125 мс) и зачисление
   (UPDATE + INSERT) не атомарны; на `bonus_claims(user_id)` нет ограничения
   уникальности. Параллельные запросы в окне антифрода зачисляют бонус
   многократно; последовательные — получают ровно один (409 на повтор).
2. **Экономика**: welcome-бонус 100, дешёвые товары (40–80) оставляют
   остаток ниже цены VIP (400) — без гонки VIP недостижим.
3. **IDOR в legacy API**: `GET /api/v1/orders/:oid` (роутер «старого мобильного
   приложения») проверяет только VIP-флаг пользователя, но не владельца заказа.
   Текущий `GET /api/orders/:oid` проверяет владельца честно.
4. **Непрозрачные идентификаторы**: публичный id заказа — `sha1(str(internal_id))`;
   числовые id маршрутами не принимаются. Служебный заказ сотрудника
   (создаётся сидером с фиксированным внутренним id) содержит флаг — участник
   перебирает числовой диапазон, вычисляет sha1 и находит нужный oid через v1.

## Решение

Полное автоматическое решение с негативными проверками честности
(одиночный повтор бонуса → 409, v1 без VIP → 403, чужой заказ через
текущий API → 403, числовой id и мусорный oid не принимаются):

```sh
python3 solve.py http://127.0.0.1:13405
```

Киллчейн: регистрация → race на `/api/bonus` (окно ~125 мс) → покупка VIP
(400 pt) → перебор `oid = sha1(id)` через `/api/v1/orders/:oid` → флаг
в служебном заказе staff.

## Структура

- `src/app/` — Express-приложение (`server.js`, `db.js`, `seed.js`,
  `lib/session.js` — HMAC-cookie, `lib/antifraud.js`, `static/`);
- `src/entrypoint.sh` — сидирование + запуск, генерация `SESSION_SECRET`;
- `src/make_public.py` — сборка хэндаута (исходники для участников, проверка
  отсутствия флага): `python3 src/make_public.py` → `public/`.
